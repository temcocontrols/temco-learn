title: "The product families"
order: 20
---

Temco's catalogue divides along the line between *controllers* — programmable devices that run Control Basic — and *everything that hangs off them*: I/O modules, sensors, meters and radios. The repository layout follows that line only roughly, so this page sorts it out.

## Programmable controllers

The T3 family. A controller is a panel with a CPU, a fixed set of I/O and a BACnet or Modbus connection, and it runs programs you write. The firmware for the whole generation lives in one repository — the STM32 build covers "all T3 controllers and the Tstat10 programmable thermostat" — and its replacement is the ESP32 build.

The model table is in [The controller model table](controller-models.md). The point ceilings are in [How many points each model carries](io-ceilings.md).

## Thermostats

Two generations, and the difference matters:

- **Tstat8** — the configurable thermostat. Legacy: its repository says so in the first line. It is configured through registers rather than programmed.
- **Tstat10 and Tstat11** — programmable, with a graphical display. The Tstat10 shares a firmware image with the T3 controllers; the Tstat11 is a separate 480 × 320 device with its own project on this site.

The Tstat8 repository points to the Tstat10E as its successor, and its source is the ESP32 repository.

## I/O modules

Boards that add points to a controller over Modbus or BACnet and have no program of their own:

- **T3-4AO** — analogue outputs, digital outputs and analogue inputs on a C8051F120
- **The Modbus and BACnet I/O modules** — the 6CTA and its siblings

## Sensors and transmitters

Devices that measure and report, with a Modbus interface and no control logic beyond optional PID:

- **CO2 sensor** — CO2, temperature and humidity for commercial and industrial spaces
- **AIRLAB** — CO2, PM2.5, pressure, temperature and humidity in one enclosure

## Meters

- **Three-phase power meter** — electrical measurement over Modbus and BACnet

## Radios

- **Zigbee coordinator and end devices** — a Modbus bridge to a Zigbee mesh, built on a TI chipset with a CC2591 front end

## What the families have in common

Every board here speaks Modbus, and most also speak BACnet. That is not a coincidence: it is what makes them interchangeable parts of one system, and it is why so much of the source is shared — the same `baclib`, the same `IO_control` library, the same FreeRTOS and FATFS trees appear repository after repository.

Those shared trees are also why README files are thin. Most of these repositories were split out of one project, so each one describes only its own delta.

---
title: "The controller model table"
order: 30
---

The controller firmware is one source tree compiled many ways. Which board it is being built for is decided in `common/product.h`, by a small set of `MINI_` constants — the firmware calls each board profile a "MINI", a name that goes back to the T3000 Mini-Panel.

## The model codes

```c
#define MINI_CM5           0
#define MINI_BIG           1
#define MINI_SMALL         2
#define MINI_TINY          3   // ASIX core
#define MINI_NEW_TINY      4   // ARM core
#define MINI_BIG_ARM       5
#define MINI_SMALL_ARM     6
#define MINI_TINY_ARM      7
#define MINI_NANO          8
#define MINI_TSTAT10       9
#define MINI_VAV          10   // no used
#define MINI_T10P         11
#define MINI_TINY_11I     12
#define MINI_T3OEM_12I    14
#define MAX_MINI_TYPE     14
```

The numbering has gaps: 13 is not defined, and `MINI_VAV` is marked "no used" in the source. The comment on `MINI_TINY` reads "ASIX CORE" and on `MINI_NEW_TINY` "ARM core" — those two names describe the same form factor built around two different CPUs, which is why both exist.

## What the codes mean

The source only comments three of them, so most of what follows is read from the names themselves — treat it as a guide to the naming, not as a specification:

| Code | What the name says |
| --- | --- |
| `MINI_CM5` | A board profile named CM5; the build switches below carry both an ARM and an ASIX form of it |
| `MINI_BIG` / `MINI_SMALL` | Large and small panel boards, on the ASIX core |
| `MINI_TINY` | Small board — the source comments this one "ASIX CORE" |
| `MINI_NEW_TINY` | The same board redesigned — the source comments this one "ARM CORE" |
| `MINI_BIG_ARM` / `MINI_SMALL_ARM` / `MINI_TINY_ARM` | The three boards above, built for ARM |
| `MINI_NANO` | The T3-Nano |
| `MINI_TSTAT10` | The Tstat10 thermostat |
| `MINI_T10P` | A Tstat10 variant; it carries more analogue inputs than `MINI_TSTAT10` |
| `MINI_TINY_11I` | Small board with eleven inputs |
| `MINI_T3OEM_12I` | Twelve-input OEM board |

The only two CPU assignments stated in the header are the ASIX/ARM pair for `MINI_TINY` and `MINI_NEW_TINY`. The `_ARM` suffix on the other three does the rest of the work. Nothing in the tree assigns a CPU to `MINI_NANO`, `MINI_TSTAT10`, `MINI_T10P`, `MINI_TINY_11I` or `MINI_T3OEM_12I` by name — they are covered by the `ARM_MINI` build switch instead.

## The build switches above them

Two sets of constants sit above the model list and select the build:

```c
#define ARM_MINI        1
#define ARM_CM5         0
#define ARM_TSTAT_WIFI  0
#define ASIX_MINI       0
#define ASIX_CM5        0
```

Exactly one of these is normally set to 1. The file also carries `SW_REV`, which is the firmware revision the build reports — `6808` in the current tree.

## Two hardware flags you will meet in the code

- `MSTP_UPDATE` — whether this build accepts firmware updates over MS/TP
- `HANDLE_REBOOT_FLAG` — a special customer build that disables the boot-time program so a controller cannot get stuck rebooting on a bad program. The comment in the source is explicit that it must stay 0 normally, and it is only for PLC builds.

The per-model point ceilings that go with each of these codes are in [How many points each model carries](io-ceilings.md).

---
title: "How many points each model carries"
order: 40
---

Each board profile in the firmware has a ceiling for every point type, and the ceilings are not proportional to anything — a big board carries fewer discrete inputs than a small one, and one small board carries more analogue outputs than a large one. These numbers are what the firmware will index; they are not necessarily what a given board is populated with.

Taken from `common/product.h` in the T3 controller firmware.

| Model | AI | DO | AO | AV | DI | SC |
| --- | --: | --: | --: | --: | --: | --: |
| `BIG` | 32 | 12 | 12 | 128 | 0 | 8 |
| `SMALL` | 16 | 6 | 4 | 128 | 0 | 8 |
| `TINY` | 11 | 6 | 2 | 128 | 0 | 8 |
| `NEW_TINY` | 8 | 8 | 6 | 128 | 0 | 8 |
| `TINY_11I` | 11 | 6 | 5 | 128 | 0 | 8 |
| `VAV` | 6 | 1 | 2 | 5 | 0 | 8 |
| `CM5` | 24 | 10 | 0 | 128 | 8 | 8 |
| `TSTAT10` | 13 | 5 | 4 | 128 | 8 | 8 |
| `T10P` | 17 | 5 | 4 | 128 | 8 | 8 |
| `T3OEM_12I` | 21 | 7 | 4 | 128 | 8 | 8 |

These are the STM32 firmware's ceilings. The ESP32 tree keeps most of them but not all — `TSTAT10` analogue outputs drop from 4 to 2, `T3OEM_12I` is gone, and `NG2`, `NEWNG2`, `NANO` and `LPWM` are new profiles with no STM32 equivalent. See [The move from STM32 to ESP32](stm32-to-esp32.md) for that comparison.

## The point-type letters

The header does not expand its own abbreviations. AI, DO, AO, AV and DI are the standard analogue input, digital output, analogue output, analogue variable and digital input; SC is used identically across every profile at 8, and the source does not say what it stands for.

## What the table says

**Analogue variables are 128 almost everywhere.** Only the VAV profile breaks the pattern, with 5 — and its whole ceiling is small: 6 inputs, one digital output, no digital inputs.

**Digital inputs appear only on the four newest profiles.** `CM5`, `TSTAT10`, `T10P` and `T3OEM_12I` all carry 8, and every older profile carries none. That is a hardware generation boundary in a single header, and it matches what the boards are: the older panels took discrete points through the analogue input cards, the newer ones have dedicated digital inputs.

**The T10P is a Tstat10 with a bigger input count.** 17 analogue inputs against 13, with every other ceiling identical. If you need to know whether a unit is the 13-input or the 17-input build, this is the difference.

**`NEW_TINY` is not a bigger `TINY`.** It has fewer analogue inputs (8 against 11) and more of everything else — 8 digital outputs against 6, and 6 analogue outputs against 2. It is a different board, not a revision.

## The VAV profile

`MINI_VAV` is marked "no used" in the model list, and its ceilings match that: 6 inputs, 1 output, 2 analogue outputs and 5 variables. Treat any code path that mentions VAV as dormant.

## Related ceilings elsewhere in the tree

`TSTAT10_MAX_*` is also used outside the controller firmware — the Tstat11 firmware in the T3-programmable-controller repository shares the TSTAT10 limits rather than defining its own, which is why the two thermostats look identical at the point-model level despite different hardware. See the Tstat11 project on this site for what it actually runs.

The `BIG`, `SMALL` and `TINY` names should not be confused with the old T3000's panel sizes. The DOS-era manual advertises "128 points per controller, expandable to 512", 48 PID controllers and 32 trend logs for a machine with a VGA monitor and a hard disk — a completely different generation, and none of those numbers come from this header.

---
title: "The move from STM32 to ESP32"
order: 50
---

Every T3 controller, and the Tstat10, once ran on an STM32F103ZE. Then it did not.

The repository that holds that firmware says it plainly:

> This is the source code to our T3 series of programmable controllers including all T3 controllers and the Tstat10 programmable thermostat. The CPU is the Arm STMF103ZE which has reached end of life for most products around Temco. Most products have been switched to the ESP32 cpu which provides an 8X increase in rom and ram.

So the split is not a rewrite for its own sake: a part reached end of life, and the replacement brings eight times the ROM and RAM.

## What this means when you are looking for code

| You want | Look in |
| --- | --- |
| Firmware for a controller still in the field on STM32 | `T3_ProgrammableController_ST` |
| Firmware for current product | `T3-programmable-controller-on-ESP32` |
| The annotated model table | either, but the ST tree's comments are fuller |
| The Tstat11 | the ESP32 tree's `main/` — it is a profile there, and it also has its own repository |

The ST tree is the better reference for *why* the firmware is shaped the way it is — the "ASIX CORE" and "ARM CORE" annotations and the customer-build switches are all there, and the ASIX-era boards only exist there. Read it for structure, and the ESP32 tree for what ships.

## The model codes survived the change

This is the useful part: the numbering is stable. The ESP32 tree keeps `MINI_BIG_ARM 5`, `MINI_SMALL_ARM 6`, `MINI_TINY_ARM 7`, `MINI_NANO 8`, `MINI_TSTAT10 9`, `MINI_VAV 10`, `MINI_T10P 11` and `MINI_TINY_11I 12` exactly where the ST tree put them.

What changed at the margins:

- The five ASIX-era profiles — `CM5`, `BIG`, `SMALL`, `TINY`, `NEW_TINY` (codes 0 to 4) — are **commented out** in the ESP32 `main/define.h`. The numbers are still reserved; the boards are no longer built.
- `MINI_T3OEM_12I` (14) is **gone entirely**: the name does not appear in the ESP32 tree at all. The OEM board's role was taken by two new profiles, `NG2` and `NEWNG2`.
- `MINI_TSTAT11` is **new at 29**, and `MAX_MINI_TYPE` moves from 14 to 30 to make room. The Tstat11 is a profile of the ESP32 controller firmware as well as its own repository.

## The ceilings did change

The point model is *not* identical, and the difference matters when you are porting:

| Profile | ST tree | ESP32 tree |
| --- | --- | --- |
| `TSTAT10` analogue outputs | 4 | **2** |
| `T3OEM_12I` | 21 AI / 7 DO / 4 AO | removed, replaced by `NG2` and `NEWNG2` |

`NG2` allows `16 + 6` analogue inputs, 7 digital outputs and no analogue outputs; `NEWNG2` allows `24 + 4` analogue inputs, 8 digital outputs and 4 analogue outputs. The `+` is part of the macro, so `NG2_MAX_AIS` is the expression `16 + 6` rather than a resolved 22 — anything that uses it has to survive that.

The ESP32 tree also adds `NANO_MAX_*` and `LPWM_MAX_*`, neither of which exists in the ST tree.

The full per-profile tables are in [How many points each model carries](io-ceilings.md).

## One conflict worth knowing about

Inside the ESP32 tree, the two headers disagree about code 8. `main/define.h` defines `MINI_NANO 8`; `main/product.h` defines `MINI_ROUTER 8`. Both are live definitions, not commented out. If you are working in that tree and code 8 matters, check which header the file you are editing includes before trusting either name.

## The display layer moved too

The ST tree drives its display directly through `display/LCD.c`, `font.c` and a driver for an ER-TFT024-3 4-wire SPI panel — a fixed panel driven from C.

The ESP32 generation, and the Tstat11 after it, use two render paths in parallel: SquareLine-generated C screens, and a JSON-driven dynamic display built on LVGL. If you are porting a screen, the panel driver in the ST tree is not the code you carry across — the layout and the widget tree are.

title: "The T3-4AO analogue output board"
order: 60
---

An I/O module with analogue outputs, digital outputs and analogue inputs, built on a Silicon Labs C8051F120 and talking Modbus. It has no program of its own — a controller drives it.

The whole repository is flat: a handful of C files in the root, with `define.h` holding the configuration and `T3IOmodbus.h` the protocol layer.

## What it carries

| | Count |
| --- | --: |
| Analogue outputs | 4 |
| Digital outputs | 8 |
| Analogue inputs | 14 |

The board's own README gives the numbers and the reason for the CPU choice: the C8051F120 includes a 12-bit ADC, which is what the 14 analogue inputs are read through. Modbus is the only field protocol listed.

## What is in the code

- `define.h` — the configuration: `MAX_OUTPUT_CHANNELS 8`, the Modbus function codes, the resistor-divider constants for the analogue inputs, and the calibration layout
- `T3IOmodbus.h`, `serial.c` — the Modbus layer and the serial port
- `Range.c` — input ranging, so an analogue input can be scaled rather than read raw
- `goalflash.c`, `flash_info.c`, `goal_flash.h` — the flash driver and the firmware/ISP split
- `LibIO_T3IO.h` — the I/O library interface
- `pic.c` — the C8051 target-specific code
- `c8051F120.h` — the register definitions for the part

## Two details worth knowing before you flash one

**The flash is split between ISP and firmware.** `DATA_TO_ISP` is `0xEE00` (60928) and `DATA_TO_FIRMWARE` is `104448` — the bootloader and the application do not share a region, and the comment for the firmware address is present with the ISP address above it, so a build has to be told which side it is going to.

**Calibration is stored as a byte.** `CALIBRATION_OFFSET 128` exists so that `FLASH_CALIBRATION` fits in an unsigned char, and `CALIBRATION_PRECISION_POINTS 10` sets the resolution. If you are writing calibration from scratch rather than through the tool, that offset is why your values look shifted.

## Input filtering

The analogue inputs are filtered in firmware, and `define.h` defines the thresholds more than once — the later definitions are the ones the compiler keeps, and earlier ones were left in place rather than deleted. Line 70 sets a noise threshold of 1 and a filter of 1; lines 76 and 84 set them to 100 and 10; a commented-out pair at line 73 would have used 200 and 10, with the comment "threshold 200/1024 = 1V". A value of 100 against a 1024-count ADC is therefore roughly a 0.1 V band, and the filter of 10 means ten samples. If you are debugging a slow or restless analogue reading, this is the block that decides it.

## Source

`T3_4AO` in the Temco controls organisation. The repository has no schematic and no manual; `define.h` and the board's README are the whole of its documentation.

title: "The Modbus and BACnet I/O modules"
order: 70
---

The `T3_Modules` repository holds the firmware for Temco's I/O modules — boards that add inputs and outputs to a controller and speak Modbus or BACnet over the field bus. Unlike the T3-4AO, these are not one board: the repository carries a family, and the README is really a build note for one member of it.

## The 6CTA, and how its firmware is built

The README describes generating a hex file for the T3 6CTA, and every step is about placing the application correctly:

1. Make sure the application address is `0x8008000`.
2. Create a hex file of the firmware.
3. Set the vector table to `0x8008000`.
4. Write the character string `TemcoT36CTA` to address `0x08008200` — the ISP tool uses this to confirm it is the right firmware for the device.

Four steps, three of which are about the same address. That is the shape of a module firmware build: the application starts at a fixed offset into flash rather than at address zero, the vector table has to be relocated to match, and a magic string at a known address tells the programming tool whether the image belongs on the board it is talking to.

If a module refuses a firmware file that is otherwise correct, the magic string is the first thing to check. It is not a version number — it identifies the board, not the release — and the README is explicit that the ISP tool is what reads it.

## Where the modules fit

An I/O module has no program of its own. It exposes points to whichever controller is on the bus, and the controller's point limits — not the module's — decide how many can be used. See [How many points each model carries](io-ceilings.md).

## Related boards

- [The T3-4AO analogue output board](t3-4ao.md) — a separate repository, separate CPU, same idea
- [The Zigbee coordinator and end devices](zigbee-modules.md) — modules that carry Modbus over a radio rather than a wire

title: "The three-phase power meter"
order: 80
---

A power meter for three-phase electrical service, reporting over Modbus and BACnet. The repository's README is one line — "Three phase power meter with modbus and bacnet protocol" — so everything below comes from the code and from the schematic in `Docs/Rev06_SCH.pdf`.

## How it is put together

An STM32F10x running FreeRTOS, with an **ADE7753** energy metering front end. `main()` starts seven tasks:

| Task | What it does |
| --- | --- |
| `PowerMeter` | Reads the metering chip and maintains voltage, current and watt-hour measurements |
| `COMM` | Modbus |
| `NET` | The network stack |
| `MSTP` | BACnet MS/TP |
| `AnalogInput` | The analogue input points a controller sees |
| `AnalogOutput` | The analogue output points |
| `LED0` | The status LED |

The application is linked at `0x8008000` — `main()` sets the vector table there explicitly, the same offset the I/O modules use, so the same bootloader arrangement applies across the family.

## What it measures

`vPowerMeterTask` initialises the ADE7753 and then loops thirty times at 100 ms, reading:

- frequency
- voltage peak and current peak
- RMS voltage and RMS current (`get_vrms`, `get_irms`)
- watt-hour calibration through the chip's CF output, when `cf_calibration_enable` is set

So the meter is measuring real electrical quantities from a dedicated metering IC, not inferring them from an ADC.

## One thing to know before trusting a three-phase reading

The phase counter is hard-coded to one phase:

```c
int8 PHASE_TEMP = 0;
...
//		if(PHASE_TEMP > 2) PHASE_TEMP = 0;
//		else
//			PHASE_TEMP++;
		PHASE_TEMP = 1;
```

The block that would step through phases 0, 1 and 2 is commented out, and `PHASE_TEMP` is set to 1 on every pass. As the code stands, the metering task reads and calibrates a single phase — `wh_calibration[PHASE_TEMP]` is indexed with that same constant, so the other two entries in the array are never touched.

Whether that reflects the shipping firmware or a work-in-progress tree is not recorded in the repository. If you are commissioning a unit, check which binary it is running before you assume three phases of measurement.

## What else is in the tree

| Folder | What it carries |
| --- | --- |
| `HARDWARE`, `STM32F10x_FWLib`, `CORE`, `SYSTEM` | The STM32F10x target and its libraries |
| `baclib` | The BACnet stack, including `baclib/object/ms-input.h` |
| `MODBUS` | The Modbus stack |
| `IO_control`, `INPUT`, `OUTPUT`, `INPUT_LIB` | The I/O layer — `analog_input.c`, `analog_output.c`, `outputs.c` |
| `FreeRTOS`, `UCOSII` | Two RTOS trees are present; the code above uses FreeRTOS |
| `TCPIP`, `uIP-1.0`, `uIP-APP` | TCP/IP stacks |
| `FATFS`, `FLASH`, `USB` | File system, flash driver and USB |
| `KEY`, `FILTER`, `VMALLOC`, `USMART`, `INFO`, `OBJ`, `USER` | Key handling, filtering, allocation, the debug shell, build output |

Two RTOS trees and two TCP/IP trees in one repository says this board was built by lifting a working controller project and adding metering to it. If you are building it, find out which pair the Keil project actually compiles — `test.uvprojx` in the root decides.

## Documents

`Docs/Rev06_SCH.pdf` is the board schematic for revision 06, and the only drawing in the repository.

`Three-PhasePower-Meter` in the Temco controls organisation.

title: "The AIRLAB air-quality transmitter"
order: 100
---

An air-quality instrument that measures five things at once — CO2, particulate matter, pressure, temperature and humidity — in one enclosure, with a Modbus and BACnet interface and enough local logic to run a PID loop and log to a flash card.

It is a much bigger project than the other sensor repository: 515 C and header files, and the folder names are the specification.

## What is measured, and with what

| Quantity | Where the code is |
| --- | --- |
| CO2 | `co2/co2.c` |
| PM2.5 and an air-quality index | `PM25/pm25.c`, `PM25/aqi.c` |
| Differential pressure | `PRESSURE/pressure.c`, `PRESSURE/DLVR-L01D.c` |
| Temperature | `TEMPERATURE/temperature.c` |
| Humidity | `TEMPERATURE/Hum_Para.c`, `HARDWARE/HUMIDITY` |

The pressure sensor is named in the source: **DLVR-L01D**, a differential pressure sensor. That matters — what it reports is a pressure *difference*, which is the right quantity for filter loading and duct static, and the wrong one if you were expecting barometric pressure.

PM2.5 comes with an AQI calculation beside it (`aqi.c`), so the instrument reports a derived air-quality index as well as the raw particulate count.

## What else it does

Beyond measuring, the tree carries:

- `PID/` — a PID loop, so the instrument can control something rather than only report
- `STORE_DATA/` — data logging to the FATFS file system
- `MENU/` — a local menu, with `menuCo2_Conf.c` and `menuCo2_Opt.c` for configuration and options
- `KEY/` — the front-panel keys
- `MODBUS/` and `baclib/` — both protocols
- `FreeRTOS/`, `UCOSII/`, `TCPIP/`, `uIP-1.0/`, `USB/`, `FATFS/` — the same stack the controllers use

The menu files are named for CO2 rather than for the air-quality unit, which is a fair sign that the menu predates the PM2.5 and pressure channels.

## Protocol

Modbus and BACnet, same as everything else in the estate. There is no register map in the repository; see the register maps project on this site for the sensor products covered there.

## Source

`CO2_HUM_PRESSURE_AIRLAB` in the Temco controls organisation. The repository has no README — the folder structure above was read from the source tree, and it is the only description of the product that exists.

The Tstat8 is Temco's configurable BACnet thermostat. It is **legacy** — the repository says so in its first line, and points to the Tstat10E as the current programmable thermostat. This page exists because the Tstat8 is still installed, still has full source published, and its revision log is unusually detailed.

![The Tstat8 board](media/tstat8-board.png)

*The Tstat8, from `Docs/Tstat8.png`.*

## Configurable, not programmable

That is the difference from the Tstat10 and Tstat11. A Tstat8 is set up by writing registers: which input is which, what the setpoints are, which icons show. There is no Control Basic program to write and no screen editor. Configuration lives in EEPROM and flash, and the modbus ID and serial number are held in flash rather than EEPROM since revision 6.1.

The repository's own summary: "Bacnet Thermostat, full featured device controls most any HVAC application. Complete source code."

## What is in the tree

| Folder | What it carries |
| --- | --- |
| `bacnet` | The BACnet stack |
| `MODBUS` | The Modbus stack |
| `EEP-MAP`, `RTE` | The EEPROM map and the runtime environment |
| `STM32F10x_FWLib`, `CORE`, `HARDWARE` | The STM32F10x target and board code |
| `FreeRTOS`, `FATFS`, `FLASH`, `FILTER` | RTOS, file system, flash and filtering |
| `include`, `USER` | Headers and the application |
| `Docs` | `Revisions.txt`, `SchematicTstat8rev4_3.pdf`, `Tstat8.png` |

Two documents matter: the revision log in `Docs/Revisions.txt`, which is the closest thing to a manual this product has, and the revision 4.3 schematic.

## What the revision log tells you

`Revisions.txt` runs from revision 5.1 to revision 6.2, covering 2017 and 2018, and it is worth reading in full before servicing a unit. The entries that change behaviour:

- **6.2** (2018-03-19) — changing the serial number caused a CRC error, because the backup copy of the serial number overlapped the CRC table
- **6.1** — the Modbus ID and serial number moved from EEPROM to flash
- **6.0** — icon output control initialisation added, plus PID sampling-time and derivative-term initialisation; a PID bug where coasting mode stayed in heat was fixed by moving the optimisation to level 1
- **5.7** — negative temperatures displayed wrongly
- **5.6** (2017-11-22) — icon output control added at **registers 783 to 791**, for nine icons: day, night, occupied, unoccupied, heat, cool, fan speed 1, fan speed 2, fan speed 3
- **5.5** — RTC single-write bug; analogue input function 2 (occupancy sensor) did not work
- **5.4** — the clock time multiple-write was not a standard Modbus command; writing a year of 2017 had to be written as 17 to be compatible with the Tstat6
- **5.3** (2017-09-11) — cooling mode sometimes jumped to heating; the PID task was merged into the control logic so the PID value could not be changed by the wrong task
- **5.2** (2017-07-20) — new BACnet library, revision 10, fixing an abort message when writing from Yabe: `BACNET_MAX_PRIORITY` must be 16

Two hardware notes are in there as well: revision 5.3 added a single hex file that works with both hardware revision 3 and revision 4, and it mentions an ION board variant (`TSTAT8_HUNTER`) whose analogue output was inverted.

## If you are servicing one

Read `Docs/Revisions.txt` first and find the firmware revision on the unit. Several of the fixes above are cases where a symptom that looks like a hardware fault — a wrong display, a mode that flips, a write that fails from a BACnet tool — was a known firmware bug with a known revision that fixed it. The log is more useful than the schematic for that.

## Source

`BacnetThermostat` in the Temco controls organisation. For the current thermostat, see the Tstat11 project on this site and the ESP32 controller repository.

title: "The Zigbee coordinator and end devices"
order: 120
---

A Modbus bridge across a Zigbee mesh: a coordinator that connects to a controller, and end devices that carry the far end of the link. Built on a TI chipset, with a CC2591 front end for range.

The repository has one source tree that produces **both** device types, decided at run time — and the revision log explains how and why, step by step, over 2012 to 2014.

## One image, two devices

From revision 10 of `Revision.txt`:

> Make two type device in one hex file, first time start up it checks which product it connected in one minute, then will remember.

So a single firmware image is flashed to every board, and on first boot it spends up to a minute working out whether it is a coordinator or an end device, then stores the answer. There is no separate coordinator build to keep track of.

## What it exposes over Modbus

The same revision entry lists the register surface:

- read and write the **PAN ID**, the **channel** and the **device type**
- read the **MAC address**
- read the **signal strength of every node** it is connected to

Earlier revisions added pieces of this: revision 05 (December 2012) added register 21 of the Tstat6 returning the PAN ID.

## How the mesh behaves when the coordinator dies

Revision 09 (April 2013) added dead-master support: an end device sends an acknowledgement request to the coordinator, and if there is no response it restores its factory settings. That is the recovery path when the coordinator has been replaced or re-addressed and the end device is holding stale network parameters.

## Radio

- TI chipset, per the repository README
- The board schematic in `Schematic/` is named `SCHEMATIC1 _ Zigbee_TI_2591_SMA_rev1.pdf`, so the design carries a **CC2591** front end and an SMA antenna connector
- Revision 04 (September 2012) added support for the CC2591 power amplifier and low-noise amplifier

Revision 07 (March 2013) dealt with the UART: Modbus messages longer than 85 bytes are sent in two packets. If you are writing a Modbus master that talks to these, that is why a long response can arrive in pieces.

## Building and flashing

Revision 08 (March 2013) added a bootloader for ISP upgrade and changed the application layout to fit behind it. As with the I/O modules, an application image built against the older layout will not run on a bootloader-equipped board.

## Source

`Tstat8-T3-controllers` in the Temco controls organisation — the name is misleading; there is no thermostat in this repository, only the radio modules. The tree has `Components`, `Projects` and `Schematic`, plus the revision log.
